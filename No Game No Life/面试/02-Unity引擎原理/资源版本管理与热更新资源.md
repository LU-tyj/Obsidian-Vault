## 一句话结论（自测用）
> 资源热更新流程：客户端对比版本文件 -> 下载差异 AssetBundle -> 校验 MD5/CRC -> 原子替换本地文件。关键设计：版本号管理、增量更新（只下载变化的 AB）、断点续传（HTTP Range）、原子替换（临时文件 + 重命名）。

## 标准答案（结构化、可背诵，2分钟内讲完）
1. **版本管理流程**：
   ```
   客户端启动 -> 请求服务器版本信息
   -> 对比本地版本号
   -> 下载差异文件列表
   -> 校验 MD5/CRC
   -> 替换本地文件
   -> 进入游戏
   ```
2. **关键设计点**：
   - **版本号文件**：维护每个 AssetBundle 的版本号和 MD5
   - **增量更新**：只下载变化的 Bundle，不是全量下载
   - **断点续传**：HTTP Range 头实现，下载中断后可从断点继续
   - **原子替换**：先下载到临时文件（.tmp），校验通过后 rename 为正式文件（防止下载到一半被使用）
3. **资源下载后的校验**：
   - MD5 校验：确保文件完整性（防传输错误）
   - CRC 校验：检测数据损坏
   - 签名校验：防篡改（可选，涉及安全）
4. **回滚机制**：保留上一版本完整包，新版本出问题时切回旧版本 + 提示用户重启

## 详细解析

### 版本文件的典型结构
```json
{
  "version": "1.2.0",
  "bundles": [
    {
      "name": "characters",
      "version": "1.2.0",
      "md5": "d41d8cd98f00b204e9800998ecf8427e",
      "size": 1048576,
      "url": "https://cdn.example.com/bundles/characters_v1.2.0.ab"
    }
  ]
}
```

### 断点续传的实现
```csharp
// 检查本地已下载的部分
long downloadedSize = new FileInfo(tempPath).Length;

// 请求剩余部分
var request = UnityWebRequest.Get(url);
request.SetRequestHeader("Range", $"bytes={downloadedSize}-");
// 追加写入 temp 文件
```

### 两层热更架构（网易常用模式）
1. **资源热更**：AssetBundle 替换（大文件，低频）
2. **代码热更**：Lua/ILRuntime/HybridCLR 替换逻辑（小文件，高频）
3. 先检查代码版本再检查资源版本，代码热更有更高优先级

### 为什么用临时文件 + 重命名？
- 下载中断：临时文件丢弃，不影响正式文件
- 校验失败：临时文件丢弃
- 并发问题：rename 是文件系统的原子操作，要么成功要么失败，没有"一半成功"的状态

## 面试官常见追问
- 如何处理多个 AssetBundle 的依赖关系版本更新？（依赖的 Bundle 版本变了，引用的 Bundle 即使内容不变也得更新 Manifest）
- 大版本更新的策略？（WiFi 预下载、后台静默下载、提示用户切换 WiFi）
- 资源下载时游戏在做什么？（通常显示更新进度条，部分游戏允许后台下载 + 资源就绪后再进特定功能）
