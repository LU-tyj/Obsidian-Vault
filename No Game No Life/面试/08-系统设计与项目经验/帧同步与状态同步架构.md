## 🎯 一句话结论（自测用）
> **帧同步同步的是"操作"，状态同步同步的是"结果"。** 帧同步：客户端上传操作，服务端广播，各客户端独立计算（RTS/MOBA/FPS）。状态同步：服务端是权威计算端，客户端只做表现（MMORPG/卡牌）。雷火面试几乎必问，且会追问一致性保证、断线重连、定点数等实现细节。

## ✅ 标准答案（结构化、可背诵，2分钟内讲完）
1. **帧同步（LockStep）**：
   - 核心：相同的输入 + 相同的时机 = 相同的表现
   - 机制：客户端上传当前逻辑帧的操作为服务器，服务端仅广播转发，各客户端本地执行完整逻辑运算
   - 实现要点：同步随机数种子、使用固定频率逻辑帧（通常 66ms/帧）、使用定点数（避免浮点精度问题）、逻辑与表现分离
   - 优点：单次数据量小、服务器压力小、易于回放、打击感好
   - 缺点：反外挂弱、对网络要求极高、断线重连复杂（需逐帧追帧）
   - 适用：格斗游戏、RTS、FPS、MOBA
2. **状态同步**：
   - 核心：服务器是权威计算端，客户端只做表现
   - 机制：客户端发送操作为服务器，服务器逻辑运算，将实体新状态广播给所有客户端
   - 优点：反外挂强、网络要求不高、玩家可随时加入
   - 缺点：传输数据量大、服务器压力大、打击感不如帧同步
   - 适用：MMORPG、卡牌游戏、休闲竞技
3. **帧同步一致性保证**：
   - 同步随机数种子
   - 定点数（Fixed-point）替代浮点数
   - 固定逻辑帧频率（不依赖 Update）
   - 逻辑与表现分离
   - 自行实现物理/碰撞（Unity 物理引擎使用浮点）

## 🔍 详细解析

### 帧同步 vs 状态同步对比总结
| 对比维度 | 帧同步 | 状态同步 |
|---------|-------|---------|
| 同步内容 | 操作指令 | 实体状态 |
| 计算权威 | 客户端各自计算 | 服务端权威 |
| 数据量 | 小（操作指令） | 大（状态数据） |
| 服务器压力 | 小（转发） | 大（运算） |
| 反外挂 | 弱 | 强 |
| 断线重连 | 复杂（逐帧回放） | 简单（直接同步状态） |
| 延迟要求 | 高 | 中等 |
| 录像回放 | 天然支持 | 需额外实现 |

### 帧同步断线重连
1. 记录每帧操作序列
2. 断线后从断点逐帧追帧回放
3. 结合状态同步做快照（定期保存完整状态用于加速）
4. 服务器可加速回放追赶进度

### 帧同步 + 状态同步 混合方案
现代商业游戏常结合两者：
- 核心战斗逻辑用帧同步（保证打击感和公平性）
- 非核心状态（如背包、等级）用状态同步
- 简称"状态帧同步"：按逻辑帧搜集变化的状态进行同步

### 定点数实现
```csharp
// 使用 long 存储定点数，如 1.5 = 1500（精度 0.001）
public struct FixedPoint
{
    private long rawValue;
    public const int PRECISION = 1000;
    
    public static FixedPoint FromFloat(float f) => 
        new FixedPoint { rawValue = (long)(f * PRECISION) };
    public float ToFloat() => rawValue / (float)PRECISION;
}
```

## 💬 面试官常见追问
- **为什么帧同步要用定点数？** → 不同 CPU/平台的浮点运算可能有微小差异（如 x86 80位内部精度 vs ARM 64位），定点数保证所有客户端计算结果完全一致
- **帧同步的服务器压力真的小吗？** → 计算压力小（只转发），但网络 IO 压力取决于客户端数量和广播策略
- **状态同步怎么做客户端预测？** → 客户端本地立即执行操作（预测），收到服务器确认后校正；如不一致则进行插值/回滚
- **雷火为什么特别关注网络同步？** → 雷火的《永劫无间》等动作游戏对同步延迟极其敏感，帧同步是核心技术栈

## ⚠️ 我曾经的误区 / 网上常见错答
- 误区：帧同步比状态同步好。两者各有适用场景，没有绝对的优劣
- 误区：帧同步不需要服务器做计算。服务器虽然不计算逻辑，但需要做帧校验和外挂检测
