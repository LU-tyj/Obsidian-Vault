## 🎯 一句话结论（自测用）
> TCP 是面向流的协议，消息之间没有边界。粘包指多个小包粘在一起（发送端Nagled/接收端缓存），拆包指一个大包被 TCP 分段。解决方案：定长消息、分隔符、或在消息头加长度字段（Length-Prefix——游戏开发最常用）。

## ✅ 标准答案（结构化、可背诵，2分钟内讲完）
1. **为什么会有粘包/拆包**：
   - TCP 是**面向字节流**的协议，没有消息边界——上层应用写的是一次"消息"，TCP 传的是一个"字节流"
   - **粘包**：发送端 Nagle 算法合并小包，或接收端一次性从缓冲区读到多个包的数据
   - **拆包**：一个消息太大，TCP 分段后在接收端需要多次读取才能拼完整

2. **三种解决方案**：
   - **定长消息**：每个消息固定长度（如 1024 字节），接收方按固定长度切分。缺点：浪费带宽（消息不满要填充）
   - **分隔符**：消息间用特殊分隔符（如 `\r\n`、`\0`），HTTP 使用的就是 `\r\n\r\n`。缺点：消息内容不能包含分隔符（需要转义）
   - **长度前缀（Length-Prefix）**：在消息头前加 2字节/4字节 表示消息体长度。接收方先读长度头，再按长度读消息体。**游戏开发最常用方案**

3. **一个典型场景**（网易互娱面真题）：
   - 发送端连续发送两个包：`"Hello"` (5B) 和 `"World"` (5B)
   - 接收端一次 recv 可能收到：
     - `"HelloWorld"`（粘包——两个包粘在一起）
     - `"Hel"` 然后 `"loWorld"`（拆包+粘包）
     - `"Hello"` 然后 `"World"`（理想情况，无法保证）

## 🔍 详细解析

**Length-Prefix 协议的实现**（游戏开发标准做法）：

```
+----------+------------------+
| 长度(2B) |   消息体(N字节)    |
+----------+------------------+
```

接收流程：
1. 先读取 2 字节长度头，得到 N
2. 循环读取直到凑够 N 字节
3. 解析为一个完整消息
4. 重复

**为什么 UDP 没有粘包问题？**
UDP 是**面向数据报**的协议，每个 UDP 报文有边界——一次 recvfrom 要么收到完整数据报，要么收不到，不存在"半个"数据报。

## 💬 面试官常见追问
- "发送两个包，一次 Receive 可能收到什么？" -> 可能收到：两个完整包（粘在一起）、一个半包、一个包多一点、单次只收半个包。所有组合都可能，取决于 TCP 分段和接收缓冲区状态
- "粘包是 TCP 的 Bug 吗？" -> 不是 Bug，是 TCP 面向流的设计特性。TCP 只保证字节流的可靠有序传输，不关心上层的消息边界

## ⚠️ 我曾经的误区 / 网上常见错答
- 误区：粘包是因为发送太快。即使发送间隔很长，只要接收端一次读得多，仍然会粘包
- 误区：UDP 不会丢包。UDP 不保证送达，只是没有 TCP 的重传机制
