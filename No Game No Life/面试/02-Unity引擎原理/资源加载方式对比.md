## 一句话结论（自测用）
> Unity 五种资源加载方式：Resources.Load（小项目）、AssetBundle（大项目/热更）、Addressables（现代化推荐）、UnityWebRequest（网络资源）、File.ReadAllBytes（配置文件）。面试必答：Resources 不能热更且全量进包，AssetBundle 按需加载支持热更。

## 标准答案（结构化、可背诵，2分钟内讲完）
1. **五种加载方式对比表**：

| 方式 | 加载源 | 热更新 | 适用场景 | 缺点 |
|------|--------|--------|---------|------|
| **Resources.Load** | Resources 文件夹 | 不支持（全量进包） | 小项目/原型 | 无法按需卸载、增加包体 |
| **AssetBundle** | 本地/远程 AB 文件 | 支持 | 大型项目、热更新 | API 复杂、手动管理依赖 |
| **Addressables** | 本地/远程（底层 AB） | 支持 | 现代化项目 | 底层仍是 AB、定制空间有限 |
| **UnityWebRequest** | HTTP 远程 | 天然支持 | 远程图片/视频/文本 | 不适用于 Prefab 和复杂资源 |
| **Csharp File API** | 本地文件系统 | 部分支持 | 配置文件、二进制数据 | 不经过 Unity 序列化 |

2. **Resources 的致命缺陷**：
   - 所有 Resources 文件夹下的资源**强制打入包体**，无法热更
   - 无法单独卸载某个资源（只能全局 `UnloadUnusedAssets`）
   - 启动时 Unity 会建立 Resources 资源索引，增大启动时间
3. **选择决策树**：
   - 原型/Demo/GameJam -> Resources
   - 需要深度定制 + 大厂 -> AssetBundle
   - 追求效率 + 中小项目 -> Addressables
   - 纯网络资源 -> UnityWebRequest

## 详细解析

### StreamingAssets 的特殊性
`StreamingAssets`（位于 `Assets/StreamingAssets/`）中的文件**原样保留**在包中，不经过 Unity 导入处理。适合放视频、配置文件、Lua 脚本等。读取方式：
```csharp
// Android 上 StreamingAssets 在 jar 包内，需要用 UnityWebRequest
// iOS/PC 上可以直接文件路径访问
string path = Path.Combine(Application.streamingAssetsPath, "config.json");
// Android 特殊处理
if (path.Contains("jar:")) {
    using var request = UnityWebRequest.Get(path);
    await request.SendWebRequest();
    string content = request.downloadHandler.text;
}
```

### 为什么 Resources 不能热更？
Resources 的资源在打包时被 Unity 编译进了 `resources.assets` 文件，这个文件的路径和内容在包体内固定。没有机制在运行时替换它——这就是 AssetBundle 存在的核心原因。

## 面试官常见追问
- Resources 文件夹可以有多个吗？（可以，任意位置创建名为 Resources 的文件夹，Unity 会合并索引）
- 为什么不在项目初期就用 AssetBundle？（开发效率低，每次修改资源都需要重新打包 AB，迭代慢）
- Addressables 和 AssetBundle 什么关系？（Addressables 底层封装了 AssetBundle 的加载、依赖管理、版本控制）
