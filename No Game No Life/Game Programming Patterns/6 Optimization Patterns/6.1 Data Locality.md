_Accelerate memory access by arranging data to take advantage of CPU caching._

## 1 Motivation 
由于CPU的缓存命中问题，我们需要优化我们的数据存储，最好将一起访问时的数据放在一起，使其在同一个缓存栈中。
>对刚访问数据的临近数据进行访问的术语叫做访问局部性

**数据局部性模式**：当代CPU带有多级缓存以提高内存访问速度。这一机制加快了对最近访问过的数据的邻近内存的访问速度。通过增加数据局部性并利用这一点可以提高性能——保持数据位于连续的内存中以供程序进行处理。

---

## 2 When & How to use it
主要是用在出现性能问题之处，而且还要是缓存未命中引起的。
>可以用[Cachegrind](http://valgrind.org/docs/manual/cg-manual.html)，但更多应该是在设计程序时就考虑让数据结构对缓存友好

缓存友好数据结构意味着减少接口（用指针或引用来访问对象，这样当然出现缓存未命中），以及减少继承等。这就意味着要与我们之前所学习的抽象化之间做出取舍。

---

## 3 Samples
下面用三个例子来实现优化。
我们的背景：游戏循环中[[3.2 Game Loop]]，每个实体被拆解成不同的域[[5.1 Component]]，比如AI、物理、渲染。GameEntity 类如下：
```cpp
class GameEntity
{
public:
  GameEntity(AIComponent* ai,
             PhysicsComponent* physics,
             RenderComponent* render)
  : ai_(ai), physics_(physics), render_(render)
  {}

  AIComponent* ai() { return ai_; }
  PhysicsComponent* physics() { return physics_; }
  RenderComponent* render() { return render_; }

private:
  AIComponent* ai_;
  PhysicsComponent* physics_;
  RenderComponent* render_;
};
```

每个组件都包含一些状态，以及更新这些状态的方法。我们每次游戏循环需要做到：
1. 遍历每个实体，为所有实体更新AI组件
2. 为所有实体更新物理组件
3. 使用渲染组件进行渲染
```cpp
while (!gameOver)
{
  // Process AI.
  for (int i = 0; i < numEntities; i++)
  {
    entities[i]->ai()->update();
  }

  // Update physics.
  for (int i = 0; i < numEntities; i++)
  {
    entities[i]->physics()->update();
  }

  // Draw to screen.
  for (int i = 0; i < numEntities; i++)
  {
    entities[i]->render()->render();
  }

  // Other game loop machinery for timing...
}
```

### 3.1 连续的数组
上面就可以看出很容易出现缓存未命中，当你遍历entities，你获得的是entity的指针，你还得去它的地址把他拿出来，然后你获得的还是组件的指针，你还得去另一个地方把这些组件拿出来。因此，我们构造一个容纳各类组件的大数组，如下：
```cpp
AIComponent* aiComponents =
    new AIComponent[MAX_ENTITIES];
PhysicsComponent* physicsComponents =
    new PhysicsComponent[MAX_ENTITIES];
RenderComponent* renderComponents =
    new RenderComponent[MAX_ENTITIES];
```
>这些是存储组件的数组而非组件指针的数组，这样我们就不再使用 `->` 操作符

```cpp
while (!gameOver)
{
  // Process AI.
  for (int i = 0; i < numEntities; i++)
  {
    aiComponents[i].update();
  }

  // Update physics.
  for (int i = 0; i < numEntities; i++)
  {
    physicsComponents[i].update();
  }

  // Draw to screen.
  for (int i = 0; i < numEntities; i++)
  {
    renderComponents[i].render();
  }

  // Other game loop machinery for timing...
}
```
这样就可以增强数据局部性。

### 3.2 包装数据
比如我们要做一个粒子系统，我们要用对其进行遍历，如果激活，那么就update。由于CPU会进行分支预测，所以我们尽可能把需要已激活的粒子都放在一块，即进行排序。我们可以当粒子激活或者反激活时，与第一个非激活粒子或最后一个激活粒子交换位置。

### 3.3 热/冷分解
一个组件中有很多的变量，包含每一帧需要检查的，和并非每帧都要用到的。以 AI 组件为粒子，前者包括 animation、goalPosition、energy等，后者包括死亡掉落物等（在实体生命周期结束时才被使用）

这些变量使组件变得庞大，导致我们一条缓存线上能放入的组件数量减少。因此我们使用热/冷分解，将我们的数据结构划分为“热数据”，即每帧需要用到的数据，还有“冷数据”，使用不频繁的数据。
将热数据不使用指针来存储，而冷数据放在一边，给它们分配一个指针。
```cpp
class AIComponent
{
public:
  // Methods...
private:
  Animation* animation_;
  double energy_;
  Vector goalPos_;

  LootDrop* loot_;
};

class LootDrop
{
  friend class AIComponent;
  LootType drop_;
  int minDrops_;
  int maxDrops_;
  double chanceOfDrop_;
};
```

## 4 Design Patterns
这种设计模式更像一种思维模式，“面向数据的设计模式”。

### 4.1 如何处理多态
最简单的方法是避开子类化的继承。[[4.3 Type Object]]中的类型对象模式就有可以实现避开子类继承而保持多态灵活。

还有为不同的对象类型使用相互独立的数组
>比如GameObject的多态有Player、Enemy，我们一般维护一个vector<GameObject*>，那可以直接为比如一个Player和Enemy分别维护一个vector。缺点就是必须时刻追踪这些集合，而且也没有多态实现的解耦。

以及使用指针集合，保存一个指向基类的指针，而不是多态继承。只是对缓存不友好。

### 4.2 游戏实体是如何实现的
就像上面的例子，游戏循环直接对组件数组进行迭代，也就是说实体本身不重要，但实体如何追踪自己的组件？

- **假设游戏实体通过类中的指针来索引其组件**
	就如第一个例子。优点是容易访问，缺点是在内存中移动组件比较困难。比如我们提到的例子系统，当我们改变内存，我们可能破话这一指针关联。
- **加入游戏实体通过一系列ID来索引其组件**
	我们可以再定义一个抽象类，来为每个组件存储一个唯一ID进行数组遍历，也可能是哈希表。这样做更复杂更慢，还需要注册
- **加入游戏实体本身只是一个ID**
	由于组件模式，其实我们的游戏实体只是一个绑定点，提供组件ID让他们互相交流，组成这个实体。这是一个优雅方便的方法，但缺点是检索一个实体的所有组件会慢，因为需要对一个对象进行ID映射。以及性能方面也会因为兄弟组件交互，导致频繁检索组件（一个解决方法是将实体ID对应为其组件所在数组的索引，但如果数组不平行的话就难说了）。
