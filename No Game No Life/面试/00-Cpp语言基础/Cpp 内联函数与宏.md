## 一句话结论（自测用）
> inline = 向编译器建议将函数体直接嵌入调用处，省去函数调用开销（压栈/跳转/返回）。但只是建议，编译器有权忽略。宏是预处理器文本替换（无类型检查、无作用域），C++ 中应优先用 inline 函数和 constexpr 替代宏。

## 标准答案（结构化、可背诵，2分钟内讲完）
1. **inline 函数**：
   - 编译期将函数体展开在调用处，消除函数调用开销（栈帧创建/销毁、跳转）
   - 只是给编译器的**建议**，编译器可能拒绝（函数体太大、递归、虚函数等）
   - 定义必须在头文件中（否则调用处看不到定义无法内联）
   - 适合短小高频的函数（如 getter/setter）
   - 缺点是代码膨胀、降低指令缓存命中率
2. **宏 #define**：
   - 预处理阶段做**文本替换**，不做类型检查
   - 只是简单替换，可能产生意想不到的副作用（如 `#define SQUARE(x) x*x`，`SQUARE(1+2)` 展开为 `1+2*1+2`）
   - 无作用域概念，容易造成命名冲突
3. **inline vs 宏**：inline 有类型检查、作用域、可调试、参数只计算一次；宏只是文本替换。现代 C++ 中推荐用 inline + constexpr 替代宏。

## 详细解析

### 编译器拒绝内联的常见情况
- 函数体太大（超过编译器阈值）
- 递归函数
- 虚函数（通过指针/引用调用时）
- 通过函数指针调用
- 包含循环的函数
- 可变参数函数

### forceinline
编译器扩展（如 MSVC 的 `__forceinline`），告诉编译器不顾代码体积也要内联。但仍有上限——上面的情况（递归、虚调用等）依然无法内联。

### 宏的副作用示例
```cpp
#define MAX(a, b) ((a) > (b) ? (a) : (b))
int x = 1, y = 2;
MAX(++x, y);  // 展开: ((++x) > (y) ? (++x) : (y))
              // ++x 被调用了两次！x 变成了 3

// inline 函数版本
inline int max(int a, int b) { return a > b ? a : b; }
max(++x, y);  // x = 2，正确！
```

### constexpr 进一步替代宏
```cpp
#define MAX_PLAYERS 100               // 宏
constexpr int MAX_PLAYERS = 100;      // constexpr — 类型安全、有作用域
```

## 面试官常见追问
- inline 函数在 Debug 模式下会内联吗？（通常不会，Debug 模式默认关闭优化以便调试）
- 构造函数/析构函数可以 inline 吗？（语法可以，但通常不应内联——编译器可能插入大量初始化代码）
- inline 函数可以取地址吗？（可以，但取地址后编译器会同时生成内联和外联两个版本）
- 宏有什么不可替代的用途？（条件编译 `#ifdef DEBUG`、编译期字符串拼接、`#__VA_ARGS__` 变参宏）

## 我曾经的误区 / 网上常见错答
- **错**："加了 inline 就一定会内联" —— 只是一个请求，现代编译器倾向于自己决定，基本忽略程序员的 inline 关键字做内联决策
- **错**："内联函数没有函数调用栈帧" —— 逻辑上存在（局部变量/参数），但不会由 call 指令创建；断点调试时可以观察到
- **错**："宏比 inline 快" —— 宏没有类型别名问题但展开后的代码体积膨胀可能降低 I-cache 命中率，反而更慢
