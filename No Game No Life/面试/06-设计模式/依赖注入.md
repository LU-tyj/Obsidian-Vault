## 🎯 一句话结论（自测用）
> 依赖注入（DI）：将对象依赖的外部实例由外部注入，而非内部创建。降低耦合、提高可测试性。替代 GameObject.Find/FindObjectOfType 的全局查找。Unity 常用框架 Zenject / VContainer。

## ✅ 标准答案（结构化、可背诵，2分钟内讲完）
1. **核心思想**：依赖倒置原则（DIP）的实现方式。高层模块不依赖低层模块，都依赖抽象
2. **三种注入方式**：
   - **构造函数注入**：通过构造函数传入依赖（最推荐）
   - **属性注入**：通过 public 属性赋值
   - **方法注入**：通过方法参数传入
3. **Unity 中的应用**：
   - 替代 `GameObject.Find` / `FindObjectOfType`（全局查找低效且耦合）
   - 用 Zenject / VContainer 等 IOC 容器管理依赖
4. **优势**：解耦、可测试（方便 Mock）、符合 SOLID 原则

## 🔍 详细解析

### 传统方式的问题
```csharp
// 紧耦合：内部直接创建或全局查找
public class PlayerController : MonoBehaviour
{
    private AudioManager audioManager;

    void Start()
    {
        audioManager = FindObjectOfType<AudioManager>();  // 慢 + 耦合
        // 或者
        audioManager = AudioManager.Instance;  // 隐式依赖单例
    }
}
```

### 构造函数注入（推荐）
```csharp
public class PlayerController
{
    private readonly IAudioService audioService;

    // 依赖通过构造函数注入
    public PlayerController(IAudioService audioService)
    {
        this.audioService = audioService;
    }

    public void PlayFootstep()
    {
        audioService.Play("footstep");
    }
}
```

### Unity + Zenject 示例
```csharp
// 1. 定义接口
public interface IAudioService { void Play(string clipName); }

// 2. 实现
public class AudioService : IAudioService, IInitializable
{
    public void Initialize() { /* 初始化 */ }
    public void Play(string clipName) { /* ... */ }
}

// 3. 安装绑定（Installer）
public class GameInstaller : MonoInstaller
{
    public override void InstallBindings()
    {
        Container.Bind<IAudioService>().To<AudioService>().AsSingle();
        Container.Bind<PlayerController>().AsSingle();
    }
}

// 4. 使用（自动注入）
public class PlayerController
{
    [Inject] private IAudioService audioService;  // Zenject 自动注入
}
```

### 注入方式对比
| 方式 | 优点 | 缺点 |
|------|------|------|
| 构造函数注入 | 依赖明确、不可变 | 参数多时代码啰嗦 |
| 属性注入 | 可选依赖灵活 | 依赖不明确 |
| 方法注入 | 临时依赖 | 不常用 |

### Unity 中 DI 的替代方案
如果没有引入 DI 框架，可以用 Service Locator 模式：
```csharp
public class ServiceLocator
{
    private static Dictionary<Type, object> services = new();

    public static void Register<T>(T service) => services[typeof(T)] = service;
    public static T Get<T>() => (T)services[typeof(T)];
}
```
注意：Service Locator 是反模式（隐藏依赖），DI 是推荐方式。

## 💬 面试官常见追问
- "DI 和单例模式有什么冲突？" -> DI 提供依赖的显式声明和可替换性，单例隐藏依赖且难测试。DI 容器内部常用单例作用域（AsSingle），但使用方不感知
- "Zenject 的绑定作用域有哪些？" -> AsSingle（单例）、AsTransient（每次新建）、AsCached（同层级单例）
- "DI 在游戏开发中会不会性能开销过大？" -> 初始化时一次性完成绑定和注入，运行时几乎没有额外开销

## ⚠️ 我曾经的误区 / 网上常见错答
- **误区**：Service Locator = DI。Service Locator 是主动拉取，DI 是被动接收。SL 隐藏依赖关系，DI 显式声明
- **误区**：DI 一定要用框架。简单项目用构造函数注入 + 手动装配即可，框架是为了规模化
- **误区**：MonoBehaviour 不能使用构造函数注入。可以用 `[Inject]` 属性注入或 Awake 后的方法注入替代
