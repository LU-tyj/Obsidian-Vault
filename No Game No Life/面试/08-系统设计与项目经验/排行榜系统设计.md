## 🎯 一句话结论（自测用）
> 排行榜系统的设计关键是选择合适的数据结构来应对不同场景。取前 N 名用优先队列（堆，O(k log n)）；频繁更新 + 全量排名用桶排序（O(1) 更新）；实时排名 + 大量玩家用跳表（Skip List）或 Redis Sorted Set。

## ✅ 标准答案（结构化、可背诵，2分钟内讲完）
1. **场景一：取全服前 1000 名，战斗力经常变化**
   - 优先队列（堆）：维护大小为 1000 的小顶堆，遍历所有玩家，堆满后若新分数 > 堆顶则替换，复杂度 O(n log k)。在线算法，不需要排序所有数据
   - 若战斗力量值范围有限（如 1-10000），桶排序更优：10000 个桶，每个桶存该分数的玩家列表，从高分桶往下取满 1000 名，O(1000)
2. **场景二：实时排名，需要查任意玩家的名次**
   - 跳表（Skip List）：O(log n) 插入/查询，适合动态数据
   - 红黑树：同样 O(log n)，但需自行维护排名索引
   - 生产环境常用：Redis Sorted Set（底层跳表），单命令 `ZADD`/`ZRANK`/`ZRANGE`
3. **场景三：排行榜分段查询（如前 1000 名 + 第 X 段排名）**
   - 数据量不大时定时全量排序 + 缓存
   - 大数据量时使用离线计算（如每小时更新排行榜快照）

## 🔍 详细解析

### 三种数据结构对比
| 方案 | 插入复杂度 | 查询 TopK | 适用场景 |
|------|-----------|-----------|---------|
| 堆（优先队列） | O(log n) | O(k log n) | 只关心 Top K |
| 桶排序 | O(1) | O(范围) | 分数范围有限 |
| 跳表 / Redis ZSet | O(log n) | O(log n + k) | 实时排名查询 |
| 全量排序 | O(n log n) | O(1) | 定时刷新、数据量不大 |

### 桶排序实现（战斗力 1~10000）
```
桶[1..10000]，每个桶是一个 List<PlayerId>
更新战斗力：从旧桶移除 -> 放入新桶，O(1)
取前 1000：从 10000 号桶往下取，直到凑满 1000 个
```

### Redis Sorted Set 应用
```
ZADD leaderboard <score> <playerId>  -- 更新/插入
ZRANK leaderboard <playerId>          -- 查询排名（从0开始）
ZRANGE leaderboard 0 999 WITHSCORES  -- 取前1000名
ZREVRANK leaderboard <playerId>      -- 倒数排名
```

## 💬 面试官常见追问
- **分数相同怎么处理？** → 按时间排序（先到排名高）或按其他维度（等级、ID）作为二级排序
- **堆方案怎么支持更新？** → 维护一个 HashMap<playerId, index> 记录位置，更新时调整堆；或用延迟删除 + 惰性移除
- **实时排行榜的数据一致性？** → 频繁写入时用消息队列缓冲 + 批量更新，排行榜允许短暂不一致（如 1 分钟延迟）

## ⚠️ 我曾经的误区 / 网上常见错答
- 误区：排行榜 = 全量排序。很多场景不需要全排序，堆/桶/跳表效率更高
- 误区：堆可以快速查询任意排名。堆只能快速获取堆顶（最小/最大），查询任意排名需要其他结构
