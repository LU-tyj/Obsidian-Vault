## 🎯 一句话结论（自测用）
> TCP 面向连接、可靠、有序，适合对数据完整性要求高的场景；UDP 无连接、不可靠、无序，适合实时性优先的场景。游戏中服务器通信（状态同步）用 TCP，实时对战（帧同步、FPS/MOBA）用 UDP。UDP 的可靠性可在应用层补充（如 KCP 协议）。

## ✅ 标准答案（结构化、可背诵，2分钟内讲完）

**1. TCP vs UDP 核心对比表**：

| 对比维度 | TCP | UDP |
|---------|-----|-----|
| 连接性 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠（确认重传、流量控制、拥塞控制） | 不可靠 |
| 有序性 | 保证顺序 | 不保证顺序 |
| 头部大小 | 20-60 字节 | 8 字节 |
| 传输模式 | 仅一对一 | 一对一、一对多、多对多 |
| 适用场景 | HTTP、文件传输、MMO状态同步 | 直播、VoIP、FPS/MOBA帧同步 |
| 拥塞控制 | 有（慢启动、拥塞避免、快重传） | 无 |

**2. 为什么游戏中用 UDP**：
- TCP 的确认重传 + 拥塞控制会引入不可预测的延迟
- FPS/MOBA 等实时游戏需要低延迟，而非 100% 可靠
- 丢失几帧数据可以通过预测/插值弥补，但延迟无法补偿
- UDP 可在应用层实现可选的可靠传输（如 KCP），比 TCP 更灵活

**3. UDP 如何实现可靠传输**（面经高频）：
- 在应用层添加：序列号、确认应答（ACK）、超时重传
- 快速重传（收到 3 次重复 ACK 就重传，不等超时）
- 流量控制和拥塞控制（UDP 本身没有，可自行实现）
- 典型方案：KCP 协议、RUDP（Reliable UDP）、QUIC

**4. 拥塞控制**（网易互娱高频追问）：
- **慢启动**：初始 cwnd 很小，每收到 ACK 翻倍增长（指数增长）
- **拥塞避免**：超过 ssthresh 后线性增长
- **快重传**：收到 3 个重复 ACK 立即重传（不等超时）
- **快恢复**：快重传后不降到慢启动，而是降到一半后线性增长

## 🔍 详细解析

**TCP 为什么慢？**
- 三次握手建立连接（1 RTT）
- 慢启动阶段吞吐量低
- 丢包后必须等待重传才能继续处理后续数据（队头阻塞 Head-of-Line Blocking）
- Nagle 算法为了减少小包而延迟发送（可能增加延迟）

**TCP 和 UDP 能否共用同一端口？**
可以。TCP 和 UDP 是不同的协议，端口号独立。同一端口号上可以同时绑定 TCP 和 UDP 两个 Socket。

## 💬 面试官常见追问
- "网络差的时候 UDP 有什么优势？" -> TCP 丢包会触发拥塞控制、降低发送速率、等待重传 = 延迟飙升。UDP 丢包直接丢弃，继续发新数据 = 偶尔丢帧但延迟稳定
- "TCP 的 Nagle 算法干什么的？" -> 将小数据包合并为大包再发送，减少网络上的微小包。但会增加延迟，游戏网络通常关闭 Nagle（TCP_NODELAY）
- "什么时候用 TCP，什么时候用 UDP？" -> TCP：文件传输、数据库、网页、MMO状态同步。UDP：实时对战、音视频流、帧同步

## ⚠️ 我曾经的误区 / 网上常见错答
- 误区：TCP 一定比 UDP 慢。TCP 在某些场景下（大文件、稳定网络）吞吐量可以很高。UDP 只是延迟更可控，并非总带宽更高
- 误区：UDP 不可靠所以游戏中不能用。UDP 可以通过应用层协议（KCP/RUDP）实现可选的可靠性，比 TCP 的全部可靠性更灵活
