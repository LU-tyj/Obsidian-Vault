## 一句话结论（自测用）
> 内存优化九条：贴图压缩（ASTC）、关闭 Read/Write、透明通道分离、降模型面数/骨骼数、少用 Resources、按需加载 AB/Addressables、Lightmap 替代实时光、控制 RenderTexture 分辨率、对象池。内存泄漏六大来源：静态变量、事件未注销、AB 未卸载、Resources 未 Unload、协程未停止、单例持有引用。

## 标准答案（结构化、可背诵，2分钟内讲完）
1. **内存优化九条**：

| 优化项 | 具体做法 |
|-------|---------|
| 贴图压缩 | ASTC（iOS）> ETC2（Android）> PVRTC（旧iOS），按平台选择 |
| 关闭 Read/Write | 贴图不勾选 Read/Write Enabled，避免 CPU/GPU 双份内存 |
| 透明通道分离 | 无透明通道用 RGB ETC2，有透明用 RGBA ASTC |
| 降模型复杂度 | 减少面数、骨骼数、BlendShape 数 |
| 少用 Resources | 避免全放 Resources（全量进包），用 AssetBundle/Addressables 按需加载 |
| 按需加载 | 不要一次性加载所有资源，场景切换时卸载旧资源 |
| Lightmap 替代实时光 | 静态物体烘焙光照贴图 |
| 控制 RT 分辨率 | RenderTexture 降分辨率 |
| 对象池 | 频繁创建销毁的对象用对象池 |

2. **内存泄漏六大来源**：
   - 静态变量持有对象引用（GC 不会回收）
   - 事件/委托未注销（`OnEnable` 注册 `OnDisable` 注销）
   - AssetBundle.Unload(false) 后资源常驻
   - Resources.Load 后未 Unload
   - 协程未停止，持有引用
   - 单例持有已销毁对象的引用

## 详细解析

### 贴图内存计算公式
```
未压缩内存 = Width * Height * 通道数 * 每个像素字节数
例：1024 * 1024 RGBA32 = 1024 * 1024 * 4 字节 = 4MB（单张！）

ASTC 6x6 压缩后 ≈ 0.5MB（约 1/8）
Mipmap 额外 ≈ 1/3（各级逐级缩小，总和的等比数列约 1/3）
勾选 Read/Write 后 = 双份（CPU 一份 + GPU 一份）
```

一张 1024x1024 RGBA32 贴图，勾选 Read/Write + 生成 Mipmap = 4 * 1.33 * 2 ≈ **10.6MB**。

### 静态变量泄漏的典型案例
```csharp
// 泄漏！
public static List<Enemy> AllEnemies = new List<Enemy>();
void Start() { AllEnemies.Add(this); }
// Enemy 销毁后，List 仍持有引用，Enemy 永远不被 GC

// 修复：OnDestroy 中移除，或用 WeakReference
void OnDestroy() { AllEnemies.Remove(this); }
```

### 事件泄漏的修复模式
```csharp
// 正确模式（Unity 标准）
void OnEnable() => EventBus.OnEvent += Handler;
void OnDisable() => EventBus.OnEvent -= Handler; // 确保注销！

// 注意：如果 OnEnable 可能多次调用（物体激活/失活），
// 需要先 -= 再 += 防止重复注册：
void OnEnable() {
    EventBus.OnEvent -= Handler;
    EventBus.OnEvent += Handler;
}
```

## 面试官常见追问
- Read/Write 为什么会导致双份内存？（CPU 需要一份用于脚本读取像素，GPU 需要一份用于渲染，两份独立存在）
- 什么情况下应该用 ASTC 6x6 vs 4x4？（6x6 压缩率更高体积更小，4x4 质量更好。UI 贴图和法线贴图用 4x4，普通漫反射贴图可用 6x6 或 8x8）
- 怎么确定一个对象是否内存泄漏？（Memory Profiler 查看引用链，看是否有"僵尸引用"——对象已逻辑销毁但仍被某处引用）
