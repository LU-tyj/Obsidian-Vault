## 一句话结论（自测用）
> C++11 引入标准线程库：`std::thread` 创建线程，`std::mutex` + `std::lock_guard` 保护临界区，`std::atomic` 无锁原子操作。游戏主线程负责渲染和逻辑，工作线程处理 IO/资源加载/物理计算等。

## 标准答案（结构化、可背诵，2分钟内讲完）
1. **std::thread**：创建和管理线程。`join()` 等待线程结束，`detach()` 分离线程（后台运行，主线程不等待）。
2. **互斥锁**：
   - `std::mutex`：基本互斥锁，一个线程 lock 后其他线程阻塞等待
   - `std::lock_guard`：RAII 封装，构造时 lock，析构时 unlock（自动管理，建议使用）
   - `std::unique_lock`：更灵活的锁，可手动 lock/unlock、可与条件变量配合
3. **原子操作**：`std::atomic<T>` 保证操作的原子性（读写/自增自减不可分割），底层用 CPU 原子指令实现，比 mutex 轻量。适用：计数器、标志位。
4. **线程池**：预创建固定数量的线程，通过任务队列分配工作。避免频繁创建/销毁线程的开销。游戏异步加载资源时常用。

## 详细解析

### mutex vs atomic
| | mutex | atomic |
|---|---|---|
| 保护范围 | 整个临界区（多行代码） | 单个变量的操作 |
| 开销 | 较大（用户态↔内核态切换） | 小（CPU 原子指令，无锁） |
| 适用场景 | 复杂的数据结构修改 | 简单的计数/标志位 |
| 阻塞行为 | 阻塞等待 | 无阻塞 |

### 死锁四条件与预防
1. 互斥条件（资源独占）
2. 持有并等待（持有资源时请求新资源）
3. 不剥夺（已分配的资源不能被抢占）
4. 循环等待（形成资源等待环路）

预防：统一加锁顺序、使用 `std::lock` 一次性锁多个 mutex、超时锁 `try_lock_for`。

### 游戏中的多线程场景
- **主线程**：渲染 + 主要游戏逻辑
- **资源加载线程**：异步加载贴图/模型，避免主线程卡顿
- **物理线程**：部分物理引擎支持分离线程计算
- **网络线程**：收发包、协议解析

## 面试官常见追问
- mutex 和 recursive_mutex 的区别？（同一线程可以多次对 recursive_mutex 加锁而不会死锁；普通 mutex 会死锁）
- atomic 的所有操作都是原子的吗？（`++`、`--` 是原子的，但 `a = a + 5` 分两步：读 + 写，不是原子的，需要用 `fetch_add`）
- 线程池的核心参数有哪些？（线程数、任务队列最大长度、拒绝策略、线程超时回收时间）
- 什么是伪共享（False Sharing）？（不同线程修改同一缓存行的不同变量，导致缓存频繁失效。解决：用 fill 变量填充到 64 字节对齐）

## 我曾经的误区 / 网上常见错答
- **错**："atomic 比 mutex 快，所以所有共享变量都用 atomic" —— atomic 只能保护单个操作，多步逻辑需要 mutex
- **错**："lock_guard 和 unique_lock 差不多" —— unique_lock 功能更多（可延迟加锁、手动解锁、配合条件变量），但稍微更重一些
- **错**："线程多了程序自然就快了" —— 线程创建/切换有开销，线程数超过 CPU 核数反而性能下降
