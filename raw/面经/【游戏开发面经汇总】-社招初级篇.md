## 前言

这是一篇超过3万字的游戏开发面试经验贴，也是面经系列的第四篇。本篇文章面向的对象由实习、校招同学逐步过渡到具有一定经验的从业人员，也就是社招。如果你是从事游戏开发中的技术岗位，尤其是图形引擎方面的，相信这篇文章一定会在你的职业生涯中起到一定的作用 *。* 另外文章中总结的很多问题，也可以作为图形引擎学习过程中的一些基础概念的补充资料。

掐指一算，已经有两年半没写文章了，为啥鸽了这么久.. 说来话长。目前我已经从腾讯离开了，从21年实习算起，到今年已有三年时间——三年之期已到，是该开启一个新的职业生涯篇章了。这次社招准备了挺久，也面了不少公司，有很多心得体会。除了技术问题之外，还有很多对社会、行业乃至人心的感悟。我想在这里分享给大家，希望能对大家有所帮助。

我会先对这次社招的面试做一个总体的概括，然后像往常一样，列出我面试过程中遇到的一些具体问题以及总结的答案和参考资料。由于个人能力和经验有限，这篇文章可能适合于三年以内工作经验的同学，当然校招生同学也是可以从中获益的。若有错漏，欢迎大家指正。

## 1\. 总体情况

我这次一共面了6家公司，9个业务部门，涵盖了游戏和非游戏行业，还包括了一家科研机构。共计18轮技术面，4轮HR面，耗时2个月，最后是拿到了两家公司的offer。过程其实不是特别顺利，有一家公司换着面了三个业务部门，有的部门面着面着HC没了，有的面着面着就发生了组织架构的变动。有些部门被HR挂了，也有的面完被泡池子泡没了，还有的的面完之后杳无音讯，甚至投完简历就石沉大海。这也侧面印证了， **最近的游戏行业和互联网行情确实是不太好** ，公司既想要经验丰富、业务对口的优秀人才，又想要降低用人成本，如果你没有满足任意一点，或者说在这二者之间取得一个平衡，那么你就很难找到一份合适的工作。但幸运的是，我对最后找到的这份工作各方面都比较满意，如今入职已经1(5)个多月了（可以看出这篇文章又拖了几个月），总体体验仍然是很不错。

参加了这么多轮面试，其实总体感受而言，社招和校招有非常多的相似之处，甚至我觉得没有本质的区别，技术上考察的内容仍然主要是涵盖计算机基础（C++、数据结构等）、算法、图形学和项目经验，只不过社招相对校招而言还有以下几点区别：

**1.更看重业务的对口程度。** 更具体地说，你是做UE还是Unity的，或者自研引擎？你是做引擎还是客户端开发？有些甚至要求具体到某一个模块功能，比如引擎方向的渲染、动画模块，客户端方向的Gameplay、系统模块。 **社招的核心是招到有相关经验、直接就能上手干活的人** 。如果你不是那么对口，很有可能连面试的机会都没有，即使你愿意转方向，愿意花时间学习。

**2.非常关注你之前的项目经历。** 简单来说，很关注你在之前的项目都做的那些工作，是否能应用到他们的项目中，产生实际的技术价值。

**3.在技术之外，会额外考察一些软性技能和综合素质的问题。** 尤其是与项目开发管理，协调沟通相关的。

此外，其实每个公司，每个面试官的风格都不太一样，游戏行业和非游戏行业又会有些许区别，有些重视基础和八股，有些重视项目经历，有些甚至以产品为导向，考察你有没有一些创造出爆款产品的思路和创意。所以社招的问题其实不像校招那样那么有确定性，八股文有，但是只占一部分，很多问题都是不确定的。

下面，我就开始介绍本次面试中遇到的一些问题，仍然是跟我之前面经系列提到的几块内容一致——计算机基础、算法、图形学、 **项目经验** ，因为我主要做UE，所以项目经验会结合UE的问题一起说。另外其中有一些问题跟我之前的面经重合，我会标注出来，尽可能精简。 **社招的重点其实并非八股文，纯图形学的问题也不多，主要是项目经验，即你已有的技术方案和工作能力，而计算机基础、算法、图形学等知识都可以在项目经验中结合进行考察** 。所以如果前面的基础部分大家如果比较熟悉，可以直接跳到第5点UE&项目经验部分观看。

**共享指针如何实现**

[Shared\_Ptr](https://link.zhihu.com/?target=https%3A//geekdaxue.co/read/jtcheng%40emcpp/item19) ， [引用计数和控制块](https://link.zhihu.com/?target=https%3A//www.cnblogs.com/paw5zx/p/18120139)

一方面要知道原始数据指针和引用计数指针的概念，还要知道构造函数，拷贝构造函数和拷贝赋值运算符都干了什么。

这里补充一个 控制块的概念 ，是一个用于管理资源的引用计数和生命周期的辅助结构。

控制块包含以下信息：

1. 引用计数：记录当前有多少个 `std::shared_ptr` 实例共享同一个对象。当引用计数降为0时，控制块会自动删除所管理的对象。
2. 弱引用计数（仅在存在 `std::weak_ptr` 时）：记录当前有多少个 `std::weak_ptr` 实例共享同一个对象。弱引用不会影响对象的生命周期，但可以用来检查对象是否仍然存在。
3. 自定义分配器和删除器（可选）：如果提供了自定义删除器，控制块会存储该删除器的副本。当引用计数降为0时，控制块会使用自定义删除器来删除对象。

控制块通常在堆上分配，以确保其生命周期与所管理的对象相同 。共享指针控制的共享资源应该有且仅有一个控制块（共享)，否则会导致资源的多次析构，进而触发未定义行为。

**两个共享指针，直接Memcpy会怎么样**

可能会遇到未定义行为，因为std::shared\_ptr内部包含了指向控制块的指针，而这个控制块管理着引用计数和其他与智能指针相关的信息。直接复制这些指针可能会导致引用计数错误，从而引发内存泄漏或双重释放。

**弱指针的作用是什么，和共享指针的区别是什么**

这里回答的要点就是弱指针不会影响共享指针的引用计数，也不会影响到资源的生命周期。实际上，弱指针和共享指针有单独的引用计数器。

这里我想到一个很好的UE的例子。UE里面有一个基于UObject的反射机制，所有的UObject对象都会纳入GC管理机制。如果在非UObject对象里面访问UObject对象，不能直接使用UObject裸指针，而要用WeakPtr进行引用。因为非UObject不会纳入GC管理机制中，保证对于UObject的生命周期管理，所以一旦这个UObject被GC掉，持有的指针就变成一个野指针了。此时如果用WeakPtr，则可以在被GC时通过Weak\_Ptr的机制得知该资源已经释放，是一个Invalid的资源。

一篇参考文章： [Unreal 浅谈TWeakObjectPtr](https://zhuanlan.zhihu.com/p/671665600) （另外较新版本的UE还提供了一个TObjectPtr功能和TWeakObjectPtr类似，但是它的使用方式跟裸指针基本一致，可以说是无痛替换了，无需将 ptr==nullptr 改成 ptr.IsValid()）

**共享指针是否线程安全**

[Boost文档: Thread Safety](https://link.zhihu.com/?target=https%3A//www.boost.org/doc/libs/1_73_0/libs/smart_ptr/doc/html/smart_ptr.html%23shared_ptr_thread_safety) ， [shared\_ptr race condition 解析](https://link.zhihu.com/?target=http%3A//www.cppblog.com/Solstice/archive/2013/01/28/197597.html) ， [shared\_ptr线程安全问题总结](https://link.zhihu.com/?target=https%3A//cloud.tencent.com/developer/article/1654442) ， [shared\_ptr多线程安全问题总结](https://www.zhihu.com/question/56836057) (这篇写得很好)

**shared\_from\_this的作用**

[enable\_shared\_from\_this类的作用和实现](https://link.zhihu.com/?target=https%3A//www.cnblogs.com/yang-wen/p/8573269.html) ， [shared\_ptr](https://link.zhihu.com/?target=https%3A//geekdaxue.co/read/jtcheng%40emcpp/item19)

这个问题并没有被问到，但是我看到UE里面其实会经常看到这样的实现，其他面经中也有看到，因此列出来。

shared\_from\_this 允许从一个已经是std::shared\_ptr管理的对象内部获取一个新的std::shared\_ptr，指向同一个对象（简单来说就是自己可以指向自己(的类型))。原因是从类对象的 this 指针 (原始指针) 来构建共享指针时会创建新的控制块，因此，如果从 this 指针构建了多个共享指针就会存在多个控制块，进而导致未定义行为。enable\_shared\_from\_this 能帮我们从 this 指针来安全的构建共享指针。

**析构函数为什么要声明为虚函数，如果不声明为虚函数，会发生什么，举例说明**

析构函数应该被声明为虚函数的原因是为了确保在通过基类指针删除派生类对象时能够正确地调用派生类的析构函数。如果析构函数不是虚函数，那么在删除派生类对象时，只会调用基类的析构函数，而不会调用派生类的析构函数。这可能导致资源泄漏和其他未定义行为，举例如下：

```cpp
#include <iostream>

class Base {
public:
    ~Base() {
        std::cout << "Base destructor" << std::endl;
    }
};

class Derived : public Base {
public:
    ~Derived() {
        std::cout << "Derived destructor" << std::endl;
    }
};

int main() {
    Base* ptr = new Derived();
    delete ptr; // 如果 ~Base() 不是虚函数，这里只会调用 ~Base()
    return 0;
}
```

为了避免这种情况，我们应该将基类的析构函数声明为虚函数：

```cpp
class Base {
public:
    virtual ~Base() { // 将析构函数声明为虚函数
        std::cout << "Base destructor" << std::endl;
    }
};
```

**一个空的类会存在什么函数**

构造、析构、拷贝构造、拷贝赋值运算符、移动构造、移动赋值运算符

```cpp
class A {};

int main
```

**一个类的空指针调用成员函数会发生什么**

这里主要考察this指针的概念，在调用一个类的成员函数时，this指针会作为参数隐式传递：

1.如果不涉及数据成员，不会崩溃；

2.如果是static函数或者只涉及static数据成员，其位于全局数据区，不会崩溃；

3.如果涉及到虚函数，有一个虚表指针的概念，此时指针为空，调用虚函数会崩溃；

测试代码：

```cpp
class B
{
public:
    void Func1()
    {
        std::cout << "hello func1" << endl;
    }

    int GetData()
    {
        std::cout << "hello GetData" << endl;
        return data;
    }

    virtual void VirtualFunc()
    {
        std::cout << "hello VirtualFunc" << endl;
    }

    static void StaticFunc()
    {
        std::cout << "hello StaticFunc" << endl;
    }

    int GetStaticData1()
    {
        return static_data;
    }

    static int GetStaticData2()
    {
        return static_data;
    }

private:
    int data;

int main()
{
    B* b = nullptr;
    b->Func1();

```

**Forward+&Cluster Shading**

[Tile Base Render (Forward+)](https://zhuanlan.zhihu.com/p/553907076) 、 [实时动态多光源渲染-基于Frustum的加速结构](https://zhuanlan.zhihu.com/p/449867303) 、 [实时动态多光源渲染-Cluster Forward Shading](https://zhuanlan.zhihu.com/p/591764319)

**Forward+**

Forward+是对传统前向渲染的一个改进，这种方法会对光源进行剔除，对于每个像素，只有对其着色有影响的光源才会参与计算。

主要有三个步骤：

（1）Depth Prepass，和Early Z类似，目的一个是为了减少Overdraw，一个是为了给后续的Light Cull提供深度信息；

（2）Light Cull，将屏幕划分为多个Tile（一般为16x16），计算每个Tile受到影响的光源，形成一个Light List。这个步骤需要构建每个Tile的Frustum，然后做求交计算；

![](https://picx.zhimg.com/v2-7b1e4d737a11868331e46384f54a7a53_1440w.jpg)

（3）Final Shading，对屏幕中的每个像素，从它所属Tile的Light List中获取光源，然后进行相应的着色计算；

**Cluster Forward Shading**

Forward+是是用基于Tile Base的空间加速结构来做光源求交计算，是二维平面的，会存在一些和深度相关的问题，比如深度不连续，最终会导致渲染的效率会和当前视角相关；

由此引出了Cluster Forward Shading算法。相比与只在屏幕空间划分Tile，Cluster方案还在Z方向向对Tile进行了划分，将Frustum划分成一个个的 Voxel（可以称之为Froxel）。Cluster的方式将空间划分的更加细了，加速结构的构建复杂度变大，内存上的消耗变多，但是规避了Tile Based方式的缺点：对象和Froxel的对应关系也会更精准，不再依赖Depth Buffer来优化，规避了深度不连续的问题，支持半透明渲染：

![](https://pic1.zhimg.com/v2-68cf8060d0c4a0e3a407a0a35ed7a586_1440w.jpg)

**移动端渲染架构（TBR、TBDR）**

[移动设备GPU架构知识汇总](https://zhuanlan.zhihu.com/p/112120206) 、 [移动端高性能图形开发 - 移动端GPU架构探究](https://zhuanlan.zhihu.com/p/363027882) 、 [浅谈Mobile TBDR GPU——引擎民工视角](https://zhuanlan.zhihu.com/p/565820105) 、 [GPU 性能迷思](https://link.zhihu.com/?target=https%3A//mp.weixin.qq.com/s%3F__biz%3DMzI3MTQzOTY3OQ%3D%3D%26amp%3Bmid%3D2247539401%26amp%3Bidx%3D1%26amp%3Bsn%3D655879683443bc2dd6b91d109b512fc4%26amp%3Bchksm%3Deb1c28273bc63356cfb326daa3c13268267753b1be7abfe0d4725600cff7b507a697b053494f%23rd)

这里首先要了解这两种架构的基本概念，其次如果能进一步说明Tiling过程具体干了什么，以及隐面剔除的具体实现流程，是最好的。做手游的话，TBR渲染架构是必须要知道的。

**概念**

TBR 即 [Tile Based Rendering](https://zhida.zhihu.com/search?content_id=250768673&content_type=Article&match_order=1&q=Tile+Based+Rendering&zhida_source=entity) ，TBDR 即 Tile Based Deferred Rendering，是相对于PC端的 IMR（Immediate Mode Renderers）的一个概念。如今的移动端硬件基本上都采用了 TB(D)R 的架构。

原因是移动端没有独立的显存，因此显存和主存是共用的，主存较小容易造成读写带宽瓶颈（而带宽消耗会影响功耗，即耗电发热会很严重）。

TBR或TBDR会将屏幕切分为一个个Tile，每个Tile有一个TileMemory，相当于GPU上的一个高速缓存。那么它在图形渲染管线中，做 深度测试，Blend还有写入ColorBuffer 就直接在TileMemory上进行，不需要和主存交换数据，降低了带宽的开销。当所有Tile绘制完成之后才会一起拷贝给FrameBuffer。

流程如下：

![](https://picx.zhimg.com/v2-6c569252c6ff0bcbb56738415bd1cebf_1440w.jpg)

在Tiling阶段，会计算每个三角形会影响(覆盖)到哪一个Tile，然后把这些三角形信息存在Tile的PrimitiveList(TriangleList)上，这个PrimitiveList会存在主存上（所以VS结束之后会有一个写入内存的延迟），然后再进行逐Tile的Pixel Shading阶段。

**TBR和TBDR的区别**

- **TBDR的特点** ：TBDR在TBR的基础上增加了HSR（Hidden Surface Removal）和Depth Test步骤，这些步骤在硬件层面上处理OverDraw问题，无需在软件层面对物体进行排序
- **TBR和TBDR的共同点** ：两者都是延迟渲染架构，通过将屏幕分割成tile来减少带宽消耗和提高渲染效率

**隐藏面剔除技术**

为了降低(不透明物体的)Overdraw，在三大主流硬件芯片的TBR架构中，PowerVR有HSR(Hidden Surface Removal)技术，Adreno有LRZ(Low Resolution Z)技术，Mali有FPK(Forward Pixel Killing)技术。

硬件的隐面剔除技术可以实现(不透明物体)的零Overdraw，而无需在软件层面对(不透明)物体进行排序。

这里根据参考资料和自己的理解做一个总结：

MSAA虽然不会执行4倍分辨率的Shading计算，但是需要存储4个采样点的ColorBuffer和DepthStencilBuffer。在光栅化阶段会对每一个像素的4个采样点做覆盖判断（这个覆盖判断应该就是是用常用的向量点乘算法来判断一个点是否在三角形内），存储在一个四倍分辨率的CoverageMask中，表示某个采样点是否被三角形覆盖。

像素着色的时候只会对像素中心的位置执行，该位置的顶点、法线、深度和纹理坐标等信息根据三角形重心坐标获得（若三角形未覆盖像素中心，则GPU会调整采样点）。如果某个采样点被覆盖到，且通过了深度和模板测试（在4倍分辨率的Buffer中判断），就会将像素的着色结果写入4倍的深度Buffer，以及更新4倍的深度模板缓冲（硬件也会有一些内存优化策略，不一定是4倍）

（有些地方说的是MSAA是计算一个覆盖率，但是我觉得上面的这个说法应该才是更准确的，它并不是根据覆盖率计算，而是把不同三角形覆盖到的采样点的着色结果放到一起来Resolve(Average)，当然如果你只有一个三角形覆盖到，那确实是根据覆盖率计算）

### 3.4 渲染排序

**1.不透明物体和透明物体的渲染顺序**

不透明物体需要从前往后排，因为硬件的Early-Z机制，可以尽早剔除掉被遮挡的像素，让它们不会进入像素着色阶段。这里稍微扩展一点，就是对于现代的移动端架构，由于有隐面剔除(HSR)机制，所以已经在硬件层实现了不透明物体的零Overdraw，此时再做不透明物体的排序是没有意义的。

半透明物体需要从后往前排，因为要遵循画家算法和Alpha Blending，才会得到正确的渲染结果。

**2.⭐渲染无关的半透明算法([OIT算法](https://zhida.zhihu.com/search?content_id=250768673&content_type=Article&match_order=1&q=OIT%E7%AE%97%E6%B3%95&zhida_source=entity))**

这个问题被问到了几次，感觉应该还是比较重要或者说有技术价值的吧，之前一直没怎么深入了解。

[顺序无关的半透明混合（OIT）相关方法](https://zhuanlan.zhihu.com/p/353940259) 、 [图形学基础 - 着色 - 透明度混合-OIT](https://zhuanlan.zhihu.com/p/368065919)

![](https://pic1.zhimg.com/v2-ecb769af48a2e234ada5117c1ae8e80c_1440w.jpg)

个人认为至少要掌握最经典的Depth Peeling算法以及Per-Pixel Linked List的基本思想。

DepthPeeling：与传统由远到近的渲染顺序算法相反，使用一种叫Under的混合顺序，可以进行从近到远的顺序进行混合。使用多个Pass来进行深度剥离，每次交替执行：（1）对所有物体(包含半透明)执行深度测试和更新深度缓冲 （2）对所有半透明物体，比较片元深度和深度缓冲，如果相等则对这一个像素执行"Under"的颜色混合，并将片元的深度值标记为一个"剥离"值，代表此层"剥离"; 反复执行（1）和（2），直到剥离完所有的半透明物体，或者a值大于一定阈值或者Pass数量达到一定值的时候停止，即得到了最终的结果。

Per-Pixel Linked List：在每个像素存储一个链表，此链表存储着这个像素重叠的多个片元的信息。通过遍历这个链表，就可以得到某个像素上所有重叠的半透明像素信息，再执行深度排序和混合计算。

2.光追需要对物体做排序吗

这个问题我理解，面试官应该是想问是否需要和光栅化渲染一样，将物体从近到远或者从远到近做排序。根据我自己之前实现的一些小项目来看，光追应该是不需要做这样的排序。因为它本身的光线求交，就可以找到最近的交点（当然这个应该是需要遍历所有物体求交之后取最小值）。虽然不需要排序，但是为了加速光线求交，光追一般都会是用空间加速结构，如BVH、KD-Tree等。

这是UE方向非常经典的一个问题， **不亚于图形学基础的渲染管线的问题** 。这种问题一般没有一个标准的答案，说出大概意思即可。主要是考察你对UE渲染管线的了解，以及是否真正有做过相关工作。这里给出我自己总结出来的一个大概的答案，仅供参考：

1.首先UE是一种多线程的渲染架构，它主要有三个线程，游戏线程（也就是主线程），渲染线程，RHI线程（可选），游戏线程负责游戏逻辑（Gameplay）的更新，渲染线程负责可见性剔除和生成DrawCall（可以进行DrawCall的缓存和合并），RHI线程负责将DrawCall转换成平台相关的图形API命令并提交给GPU，它们之间会间隔一帧。游戏线程是和渲染线程分离的，游戏线程的每一个可以绘制的对象，在渲染线程都有对应的代理，由代理负责渲染出来。

![](https://pic2.zhimg.com/v2-9feeb5415f2bed4045ecfc19875411e5_1440w.jpg)

2.其次UE的渲染管线有两种绘制路径，一个是 静态绘制，一个是动态绘制 ，静态绘制只需要生成一次绘制命令，然后就可以缓存下来多帧复用（如果没有触发重新生成的条件，就可以一直复用用），比如静态网格体，动态绘制路径就是需要每一帧去动态生成，比如骨骼网格体等。

![](https://pic2.zhimg.com/v2-331681c5247189d97ebf45ac63a145ed_1440w.jpg)

3.然后它有几个关键概念，一个是MeshBatch，一个是MeshDrawCommand，一个是MeshPassProcessor

![](https://pic2.zhimg.com/v2-82ca89433a6978226435b11ddc77ab81_1440w.jpg)

`MeshBatch` ：使用相同材质和Vertex Buffer的一组网格数据，由每一个Proxy调用 `GetDynamicMeshElement` 函数生成，它是Proxy和MeshDrawCommand的中间数据，主要是解耦PrimitiveProxy和各个MeshPass，因为一个MeshBatch可能会在不同的MeshPass绘制，比如DepthPass，BasePass，TranslucentPass，等等  
  
`MeshDrawCommand` 是MeshBatch转换为的特定的MeshPass的绘制命令，是状态无关的渲染描述，存储了RHI所需要的所有信息，可以理解为DrawCall的最后一个状态了，可以在这一层执行 **Cache和Merge**  
  
`MeshPassProcessor` 是特定于某个MeshPass的处理器，它会选择合适的Shading Binding并生成MeshDrawCommands，这一步是并行的

4.具有高度的并行性  
(各个) pass setup是并行的（动态命令生成、排序与合并）  
(各个) pass 发起Draw call(draw dispatch) 也是并行的（当然只是记录在RHICmdlist里面，后续由RHI统一发起驱动层的真正绘制）

垃圾回收使用一种叫标记清除法的技术。会有一个全局的根节点，和一个树状结构来存储所有加入GC的物体节点，当一个物体生命周期结束的时候会把它标记为dead，此时该节点在树状结构中不可达。从根节点遍历的时候发现某个节点不可达就进行GC。

标记清除法 会分标记和清除两个阶段

（1）标记阶段，首先把所有对象标记为不可达，然后再从根节点开始遍历，检查可达性，如果可达标记为可达（这部分是多线程进行）。

每一个UObject实例化的时候，会被加入到一个根节点 `ObjectsToSerialize`

检查可达性的时候，利用了UObject的反射机制，根据UClass检查该UObject的每一个UProperty，提前按照自定义的格式生成一个Token流，这个Token流实际就是UObject对象的引用链。

（2）清理阶段，分为 收集，清理，析构三个步骤。

首先，UE会把所有的不可达的Uobejct收集到一个GunreachableObjects列表里（多线程），这里有一个Cluster机制，表示同一生命周期的一组数据；

然后，增量清理，调用 `ConditionalBeginDestroy` 和 `ConditionalFinishDestroy`

最后在 `TickDestroyObjects` 调用每一个要销毁对象的析构函数，

**7.UE的智能指针，是否线程安全，和原生C++的智能指针对比呢**

这个问题当时我并不是特别确定，面试官给我的答案是UE的智能指针(这里主要指Shared\_Ptr）的引用计数是原子性的，引用计数就像是一个闸门，只要引用计数线程安全了，共享指针就线程安全了。并说UE共享指针和原生C++的区别就在于这个引用计数的原子性上面。但是我觉得不太对，参考我上面2.1中的线程安全那一节，实际上原生C++的引用计数也是原子性的。如果有朋友有更权威的解答可以指正。

另外关于UE智能指针的问题，我曾经在某地方(你懂的)看到过一篇专门的文章。上面提到了它和原生C++的异同点，我觉得还是比较靠谱的（但这个需要了解一些UE智能指针的具体上下文）：

1\. 相同

- 智能指针的设计目标上是一致的，TSharedPtr、TWeakPtr、TSharedFromThis、TUniquePtr分别解决了资源释放、资源共享、循环引用、自引用的问题和资源的独占。
	- 共享指针的结构上也相同的，TSharedPtr、TWeakPtr指针。有两个成员变量，TSharedFromThis持有1个自身的TWeakPtr指针。
	- 共享指针的功能上基本一致，TSharedPtr有完整的SMF(啥意思?)和箭头操作符，TWeakPtr通过IsValid()和Pin()判断资源是否有效和获取资源的TSharedPtr指针。
	- 独占指针TniquePtr同样通过禁用复制构造、赋值操作符保持了资源的独占，同时也提供了move构造和move赋值支持资源的转移。

2\. 不同

- 分别为TSharedPtr、TUniquePtr提供了引用版本TSharedRef、TUniqueObj。
	- 提供MakeShared函数返回资源与控制块聚合的共享引用TSharedRef。
	- 共享指针不提供分配器的能力，简化智能指针的处理。
	- TSharedFromThis只返回共享引用TSharedRef，不返回TSharedPtr。
	- TUniquePtr的删除器以继承的方式保存，而标准库使用组合的方式。

另外很重要的一点是，UE的共享指针提供了两种线程安全的版本，即分为线程安全版本和线程不安全版本。线程安全版本使用原子计数器增减计数器，并可以根据平台使用不同的原子操作。

线程非安全版本直接操作计数器，效率更高。

在控制块方面，unreal和标准库的实现区别是比较大的：标准库接口简洁，功能内聚，而Unreal根据使用场景的不同做了针对性的处理。

关于UE粒子系统的合批，我主要参考的是这一篇文章 [在UE4中实现跨Emitter的粒子合批绘制 - 知乎 (zhihu.com)](https://zhuanlan.zhihu.com/p/381983794) ，这里的粒子系统指的是UE4中旧版的Cascade粒子系统。Cascade和新版的Niagara粒子系统均实现了发射器(Nigara是Renderer）内部的Instancing合批，但是并没有实现不同实例之间的合批（简单来说，一个粒子系统资产，拖动到场景中会生成多个PS实例，但它们之间并不会自动进行合批，即使内部的发射器是完全一样的。

Cascade内置的合批使用的是VertexBuffer来作为Instance Buffer，一块Buffer 64KB，而一个Particle的数据大小是64B（Sprite类型），因此可以支持1024个粒子实例。Niagara使用的是Uniform Buffer，一块Buffer多大以及能支持多少个粒子暂未了解。其实 **关于Instance Buffer使用VertexBuffer还是UniformBuffer更好** 似乎并没有一个权威明确的答案。我这边的Leader说他们之前部门有一个人做过相关测试，最后的结论是性能差别不大。之前看到的一种说法是UB的大小是有限的，所以可能无法支持数量过大的Instancing合批的场景（然而VB的大小应该也是有限的？）在Google到的一些答案 [Vertex buffers vs. uniform buffers for instanced rendering: r/webgpu (reddit.com)](https://link.zhihu.com/?target=https%3A//www.reddit.com/r/webgpu/comments/14ups8v/vertex_buffers_vs_uniform_buffers_for_instanced/%3Frdt%3D51672) 以及GPT的回答中，均提到VB的性能更高，可以支持更多数量的Instance。

在这篇文章中，判断 **是否能合批的条件** 是粒子的类型以及材质。但是在实际应用中，仅仅考虑这两个因素是远远不够的，会产生很多Bug。可以参考UE内部实现的动态合批考虑的因素：

**4.自我认知&职业规划**

1. 你觉得你自己的优势和劣势是什么？
2. 如果你来这边，你觉得你能带来什么价值？
3. 给自己打分，在 性能优化、效果开发、引擎系统开发、美术工作流 这几方面打分，打多少分？
4. 你对自己的技术栈是怎么考虑的（偏工程，算法？）
5. 你更倾向于做PC还是手游？
6. 你对我们这个部门的了解如何？| 对我们项目情况的了解，是否能接受？
7. **为什么选择来XX(地点)？| XX地点是否能接受？**
8. 未来5年职业规划
9. **为什么考虑跳槽**

这方面是对职业规划方面的一些考察，其中最喜欢问的一个问题就是 为什么考虑跳槽 ，其实这个也很容易理解，你身边有人要跳槽，你第一想法也是问他为什么要走嘛。这里面潜藏一个担心，就是你是不是犯了什么事走的，比如弄了个什么重大事故被干掉了，或者是能力不行被淘汰了，又或者性格极端、脾气古怪，跟领导和同事关系搞不好之类的。只要你不是由于负面原因跳槽的，其实都不会有什么大问题。这个问题实际上在业内有一些 "标准答案" ，虽然我觉得有些冠冕堂皇，但是为了生存，建议大家还是遵循一下游戏规则。关于地点，面试官(HR)也很喜欢问，因为地点确实是职业选择的一个重要因素吧，我这次是换了城市，所以很多面试官担心我是否是真的愿意过去。

### 1\. 为什么鸽了那么久

（1）技术焦虑

自从进了腾讯之后，我逐渐惊奇地发现，自己曾经在知乎上看的一些技术文章的作者，竟然就是自己的同事，毛哥自不必说，除了他以外，还有3位在业内有一定影响力的知乎大佬（有两位都是粉丝过万的），竟然就是同组的同事。更不用说还有一些其他部门的同事，有很多我都是学着他们的文章过来的，这种体验真的非常奇妙，你曾经仰望的技术大佬，就在你身边，你还能跟他们以同事甚至朋友的身份交流，仿佛自己也是拥有了跟他们一样的能力一般。

但随着工作越久，就越发现自己和他们之间的差距之大，部门和公司内优秀的人实在是太多了，在见识了真正的技术实力之后，我开始产生了技术焦虑， **突然觉得自己之前写的东西显得有些肤浅，无非只是一些基础知识的梳理、总结和搬运罢了，并没有什么技术深度，技术价值也很难说有多大** —— 人家真正有技术实力的人都没怎么表露自己，我在这叭叭叭地写些表面的东西，岂非可笑 ？当然，我不是没想过写一些更有深度、更具体的技术文章，但此类文章一方面需要很深的积累，另一方面往往吃力不讨好，看的人不一定很多，由于各种原因又搁置了（当然，我很Respect那些写深度技术文章的博主，我自己也一直在从中受益，后面我或许也会尝试写一些有深度的文章）

于是在这种技术焦虑下，我经常会否定自己以及做这些事情的价值，也逐渐失去了更新的动力。只是后来我也慢慢相通了，并意识到这种思想的狭隘性。在这里我想引用我很喜欢的一篇博客中讲到的话：

![](https://pic4.zhimg.com/v2-3864ac886d52e8f82dcb56649c6afb27_1440w.jpg)

**"闻道有先后，术业有专攻"** ，我本身是一个跨专业转计算机的人，在学习时间和投入的精力上可能比不过一些科班出身的人，而在天赋上，我也比不上那些真正的天才，再加上近些年来我的心态其实是一种比较反卷和躺平的心态，并没有花太多的业余时间去提升自己的技术能力（这里不推荐大家也这么做），因此在技术实力上比不上那些真正的技术大佬是很正常的事情。而我也逐渐意识到， **我的优势，并非在于对这种高深技术的钻研上，而是我能用通俗易懂且尽量精炼的语言去总结和传递一些基础知识，去引领那些对于游戏开发不太了解的同学去跨入游戏开发的大门，以及通过我的经验去帮助他们获得一份更好的工作** 。我觉得这才是我以及我所写的文章的真正价值。我不应该深陷于同辈压力、技术比较，以及自身不足的"小我"意识上，而是应该充分发挥自己的优势，去努力做更多有意义的、有价值的事情，给更多人带来帮助。开拓技术的边界是一种道，而引领更多人进入游戏开发的大门也是一条路，这也是所谓的"术业有专攻"。如果太过在意外界评价以及陷入自我内耗，只会什么事也做不成。

（2）意外事件

关注我比较早的人应该都知道3年前的那件事，毛哥的离去对我也产生了非常大的冲击。看着他呕心沥血，夜以继日地翻译、写文章，努力工作，待人友善且无私。但是最后却落得这样一个下场，我突然产生一种无力和虚无感，觉得做什么事情都没有意义——再如何地努力、奋斗，取得多大的成就又有什么用呢？最终不过是一场空。某种程度上来说，也是陷入了一种虚无主义中，所以在那之后的很长一段时间里，我都不是很想写东西。

（3）工作压力

这件事情之后，我们部门合并到了另一个部门，也参与了一个新的项目。随着项目的进行，我们的作息从双休，变成了大大小周，然后变成大小周，最后临近上线前半年多，变成了单休。当你发现你周末只有一天休息时间的时候（即使最开始只是大小周），你会发现， "我TM不是昨天才上过班么，怎么明天又要上班了？" ，这种时候，你光是休养、回复元气，1天时间已经不够了，更不用说还时不时情绪爆炸，需要报复性玩游戏和出去玩来安慰自己，基本上就没额外的时间和精力去写文章了。

这些就是我为啥这么久都没更新文章的主要原因，不过无论如何，这三个原因目前都已经逐渐消退了，所以我也是在努力打起精神来恢复我文章的更新。

### 2\. 新的身份

我如今是跳槽到了一家中大型的游戏公司，而承蒙公司的信任和认可，我入职后不久就 **成为了公司的技术面试官，负责校招、实习等招聘的第一轮面试** 。不当面试官不知道，其实大公司的面试都是有非常严格的流程规范，对考察的内容、评判的标准，以及沟通的方式、面试的礼仪等都有比较严格的要求。而在面试内容这块，我惊奇地发现， **公司要求考察的面试内容分布，竟然跟我整个面经系列的划分不谋而合，几乎一致** 。在技术侧，要求考察的内容有： 编程语言(C++、Lua等）、编码能力、数据结构和算法、操作系统(计算机组成)、图形学、网络编程(可选) ，这个直接可以看一看我面经系列文章中一直在提的四大部分几乎完全一致。

![](https://picx.zhimg.com/v2-370647ba8e392b70e336fb75921320a5_1440w.jpg)

而这也确实跟我之前参与过的这么多轮的面试体验一致，应该是大公司都会遵循类似的一套规范。不瞒你说，我就是带预言家。

如今，以一个面试官的身份再来看游戏开发的面试，又会有不同的体会，其中感触比较深的两点如下：

（1）面试官并非一无所知，在某个领域，甚至还不一定比你了解。

技术领域的知识浩如烟海，具体的方向内容也五花八门，像我面试的时候就遇到过一些做几何的、AI的，这些东西我就不是很懂。而即使是渲染，如果是我自己没做过的方向，可能也不是很了解。这种时候其实面试官要评估一个候选人的能力就比较困难，因为他不知道这个技术的实现难度和价值在哪里。 这种时候你需要做的，就是用通俗易懂的语言给面试官介绍清楚原理，并且尽可能把你这个技术描述得很牛逼，创造了很多价值(自信点)。像我第一次面的一位同学，他说他做的东西被拿到GDC上去分享了（他是腾讯的实习生，应该是被Leader当作GDC分享的一部分内容那种），我寻思woc这有点厉害啊，无论我懂不懂这个技术，先高看他一眼再说。不过招聘方也并非没有应对方式，首先会尽量指派对口方向的面试官去面试，如果没指派对，面试官对不熟悉领域不好评估的话，他会将面试结果设置为待定，然后让更熟悉这块领域的面试官去再考察一轮。

（2）面试官很喜欢问你他最近遇到过的问题，或者他做过的一些技术。

这个无论是我在观察我直属Leader的面试过程，还是我自己面试都很喜欢问。这单纯是处于一种好奇的心理，想知道候选人在面临自己所遇到的问题会想出什么解决方案（但这并不算是套方案，因为往往问题已经是解决了）。这一点就会给面试带来一些不确定性，毕竟遇到的问题肯定是多种多样的嘛。比如如果你遇到我，就可能会被问到一些头文件包含、链接错误问题的原因和解决方案，以及把多个不同因素Pack成一个GUID的方案等问题。当然还有很多面试官会关注的细节，这里就不一一列出了。

从面经系列的作者，到成为面试官，是一种挺神奇的体验，或许也是一种命中的机缘。 **所以我想说的是，在面试求职这方面，你仍然可以选择相信我。**

### 3\. 文章更新计划

我未来仍然会把面经系列的文章作为主要的更新方向，这一篇是偏技术业务部分的，之后打算介绍 **一些非技术相关的问题和具体的求职准备步骤。包括如何收集资料，如何制作简历，如何提炼项目技术点，如何做自我介绍，以及HR面试的注意事项和最终Offer如何选择等** ，还会涉及如何与猎头合作，与HR沟通等。很多工作经验较少的朋友（尤其是学生）可能会低估了社会的复杂性和人心的险恶。当然，写什么也取决于大家的反馈，其实这么久以来 **大家最关注的一个问题还是项目如何准备的问题** ，这个问题我其实评论区和私信都被问了无数遍，这次我也可以看看这篇评论下面大家最希望看哪方面的内容，然后决定写什么。

但在这之前，下一篇文章，我会先回应大家关注很久的一个问题。我的主页上至今都保留着一条21年时候的想法，这也是我仅有的一条想法， **一直没删除是因为我想着总有一天要来实现当初的承诺** 。下个月刚好是毛哥离开三周年， **我会重新写一篇文章来缅怀他** 。时过境迁，斯人已逝，我无意再起风波，只是对大家当年疑惑的问题，以我一个身边人的视角给出一个我认为的回答（并非一定对）。他这样一个对中国游戏行业都产生影响，留下熠熠光辉的人，或许应该让人们更加了解他，以及被记录些什么。但我不希望这篇文章会产生不好的影响（尤其是对他的家人），所以我会视情况而关闭评论区，甚至删除文章，希望大家理解。

### 4\. 个人的打算

写了这么多面经系列的文章，从表面上看，我自己也在秋招和社招的时候都找到了比较满意的工作。似乎只要按照这些文章中的内容去准备，稳扎稳打，就都能找到一个不错的工作，但真的是这样吗？？

前段时间我关注了知乎的一个问题 [图形学秋招快抑郁了，有没有大佬能指条明路? - 知乎](https://www.zhihu.com/question/665561463) 。我看到了很多人艰难的求职境遇和唱衰的声音，而我也去跟实验室今年毕业的学弟沟通过，才知道即使是浙大CAD，在去年环境最差的时候，基本上人均也只拿到了一个offer，这跟我毕业的那几年，每个人都能拿好几个offer形成鲜明的对比。我又想到了我今年还在腾讯时候来的一个北大本科毕业，在欧洲读硕士的实习生，他工程能力非常强（比我实习的时候强不知道多少倍），工作也做得很好，但最后还是因为部门没有HC而没有被留用，我十分感慨和可惜。其实这个世界很残酷，也根本没有绝对的"公平"一说，无论你个人能力再强，你仍然拗不过大环境的浪潮。

这个时候我耳边才回响起那句警世格言—— **“每当你想评判任何人的时候，不要忘记，不是每个人都拥有你这样的条件”** 。我意识到，我能够找到一份好的工作，可能并非是因为我的能力有多强，很大程度是我蹭到了实验室的光环（我的能力在CAD里面是属于绝对的平庸级别，这点并不是谦虚），以及碰到了一个好的时候。21年之后，互联网和游戏行业的情况急转直下，HC全面收缩。但即便有了运气加成，我最终能上岸的过程并不轻松，实际上我也经历过艰辛的考研经历，以及遇到过重大的人生挫折，这点我不展开，后续有机会再跟大家分享。

这些事情让我重新审视，其实图形引擎岗在游戏行业也是一个非常小的领域，整体来看岗位需求并不多，一般至少要中大型公司才会有。我根据自己的经验体感来估计，一个100人左右的项目，可能只需要个位数的引擎+TA，大概就是5个吧，远远不如策划、程序、美术这种主要的岗位需求量大。而且现在很多引擎和TA岗位是以中台的形式存在的，这样很多技术可以复用了，如果按项目来招引擎TA就很不划算。

**所以我想，如果只是做图形引擎相关的内容，能帮助到的人不多** ，而且我也发现，网络上关于游戏客户端开发的文章似乎不是很多（也许只是因为信息茧房，我刷到的不多）。之后想做的内容，应该会不仅仅包含图形引擎岗，而是包括了游戏客户端开发在内的更多游戏技术岗位（乃至非技术岗位）。其实这些年以来我也一直持续关注着游戏行业的发展，包括B站的一些Up主如芒果冰等都对我进入游戏行业产生了很大的影响，如今身处于游戏行业，我能了解到更多的信息，也希望能做一些分享。

在我发表面经系列文章之后的这些年，我在私信和评论区都回复了很多朋友的问题，也真正地帮助了很多朋友找到了实习或者工作的机会，成功上岸，比如下面这两位，最后都成功进入了腾讯实习：

当我看到他们给我发来的感谢的时候，我内心也充满了满足感和成就感，我觉得我做的事情是有意义的，真正能帮助到他人的。我回想起当年萌生出转行念头之初，内心也充满了迷茫与焦虑， **我心中期待的，正是有一个有经验的前辈，可以给我指点迷津** 。我当时确实也咨询过一些知乎大佬，他们也非常谦虚且有耐心地回答了我的困惑，我十分感谢他们，以及感谢知乎有这样一种友好的氛围。我此刻做的一切，恰如是对当年那些替我指点迷津的大佬的传承，有种薪火相传的意味。 **从某种程度上来说，我似乎找到了另一个人生目标，以及一种使命感。我期待能帮助更多的人跨入游戏开发的大门，去找到一份自己热爱且能够得到不错回报的工作，从而改变自己的命运** *。* 我承认人具有一定的局限性以及大环境的残酷，但我始终认为人对自己的命运仍有一定程度的掌控，某些时候，我们依旧需要保有那一点"人定胜天"的勇气。

关注我的朋友应该发现，我在知乎上开启了付费咨询，实际上我的初衷并不是赚钱，我的咨询费用极低（3块钱，扣去平台费用到手还不到2块钱），相对我工作的时薪来看，这点收入是远不够看的。我这么做是想筛选掉一批不真诚和不礼貌的人，因为很多人会自己都没想清楚就问一些莫名其妙或者不相关的问题，或者不具备基本的礼貌。回答问题是需要消耗时间和精力的，即使我乐意帮助别人，以我现在的条件和精力，也无法支持太多这种繁杂的工作。我期待能得到更多的激励和正反馈，无论是个人的影响力、发展还是实际的收益，又或者仅仅是言语上的感谢，这样我才更有动力坚持下去。

所以我想说的是，为了把这件事做大做强， **我后面可能会尝试做一些自媒体的事业** ，内容当然是游戏行业相关，主要包括 **游戏开发入门** ，如学习路线、项目准备等，还有 **游戏开发面经系列** ，如求职准备、面试技巧等，然后还会分享一些 **个人的经历** ，比如我当时是怎么转行的，标题我都想好了—— "我是怎么从土木天坑 (恒大) 到游戏天堂 (天美)的" ，其实这段经历也挺精彩，大伙看看这个标题是不是足够吸睛(Doge.jpg)。另外可能还会分享 **游戏行业的那些事** ，比如我在网易的经历、腾讯的经历，他们里面的一些组织运作模式，一些行业的潜规则和小八卦等。

具体形式，知乎这边肯定是以更新专栏文章为主，短视频的话，(可能)计划去B站开个账户（还有抖音、小红书、视频号之类）。另外还打算接一些 **私人咨询的业务** ，不过这块我没想好，暂时就在知乎上提供吧，费用会提高一些，但也不会很高，我知道大家都不容易（只是如果能对你职业发展有帮助，请我喝个奶茶总不过分）。当然这些都只是个初步的设想，毕竟人生在世，总想做出些有价值、有意义的事情， **但真的能不能做下去，做起来，也取决于这些内容是否被大家认可吧** （现在也只是想想），毕竟我知道真正能做起来的人很少。

所以，这里当然是 **希望大家能多点赞、收藏、评论、转发以及关注我** ，这对于一个事业起步阶段的人来说非常重要（万一以后做起来了，现在关注的就是老粉了(嘿嘿)），大家的支持是我继续写下去的重要动力。

另外，从今天开始，我在互联网上将有一个新的名字： **不羁的游侠** ，你们从此可以叫我 **羁友** （有羁绊的朋友）。这个名字包含了几个对我产生过影响的重要因素，首先一个是我一直喜爱的传统武侠文化、侠义精神，因此有"侠"。而不羁，是我童年时期很喜欢玩的一个游戏《QQ幻想》中，剑客职业在18级之后得到的一个称号——"不羁的剑客"，我从此喜欢上了这个词语，另外"羁"，恰好跟我最喜欢的动漫之一《火影忍者》中强调的伙伴之间的 **羁绊** 有一定的关系。至于游，一方面当然是我们所热爱的游戏的"游"了，另一个含义，其实来自于我最近很欣赏的一个自媒体博主"数字游牧人"，我觉得他很容易成为现代年轻程序员的一个榜样或者说偶像，潇洒不羁的外形、幽默搞怪的性格，才华横溢的实力，当然还有他非常令人羡慕的高薪又自由的"数字游民"的生活。游侠，一开始我是从以前玩的《帝国时代》中的强力兵种"骑兵-游侠"得到灵感，后来觉得又能和数字游民和武侠文化结合。综合这几个因素之外（再加上"基友"的谐音梗），不羁的游侠这一完美名字应运而生。希望它以后能成为对游戏行业有帮助的名字。
